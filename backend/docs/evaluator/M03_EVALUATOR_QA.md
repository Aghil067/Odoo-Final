# M03 evaluator questions and answers

1. **What business problem does M03 solve?** It turns a qualified customer's internally approved survey into a proposed system with selected technical components, compatibility findings and a historically accurate material BOM. It does not manage warehouse stock or install equipment.
2. **Why can it not start from any lead?** It uses M02's latest eligible approved-survey guard and exact review/version, inside the M03 write transaction. Pending, rejected, canceled, superseded or ineligible survey references cannot be used for approval.
3. **How is cross-customer mixing prevented?** Server derives lead/site/customer from the M02 handoff. Composite PostgreSQL FKs match those identities and the exact survey review/version. User-supplied customer identities are not accepted in creation bodies.
4. **What is a template versus a configuration?** A template is a reusable starting point and default requirements, not approval. A configuration is one customer's explicit system/phase/capacity/assumptions and selected components, reviewed independently.
5. **What keeps template changes from altering old designs?** Every master change creates an immutable SolarTemplateRevision. A configuration stores its selected version and full snapshot. Existing BOMs also retain their own component/specification/price snapshots.
6. **Why not put stock quantity on SolarComponent?** It defines a product's SKU, technical facts, unit/cost/warranty/serialization policy. M04 will own actual stock by location, reservations and serial movements. A BOM quantity is a requirement, not on-hand inventory.
7. **How does Prisma differ from a query builder here?** Prisma generates typed model/relation APIs and ordinary migrations from the schema. A query builder primarily composes SQL-shaped queries. PostgreSQL still enforces keys/constraints; custom SQL is needed for immutable guards not represented by Prisma's DSL.
8. **What do foreign keys enforce?** Parent records must exist. The composite configuration survey FK enforces lead/site/customer matching; a second composite FK enforces review ID/survey ID/content version matching. Delete restrictions preserve linked business history.
9. **Why normalize these tables?** Reusable catalog/template definitions are separate from customer revisions and BOM lines, reducing duplication/update anomalies. Deliberate immutable snapshots duplicate selected facts to preserve what was actually reviewed/costed.
10. **Why Decimal instead of JavaScript numbers?** Binary floating-point can introduce rounding noise in money. The module uses Prisma Decimal/Decimal.js with 48-digit context, explicit HALF_UP line rounding and string JSON inputs/outputs. No client totals or implicit FX arithmetic are trusted.
11. **How is a BOM amount calculated?** Quantity times snapshotted price, rounded to two decimals per line. Header/category totals sum those rounded amounts. Prices retain four fractional digits; quantities retain three. Unsupported mixed currencies and numeric overflow are rejected.
12. **What if the catalog price changes?** Existing lines retain their price/version/snapshot. A draft can explicitly refresh from the current catalog. Current inactive or changed versions block approval until deliberately refreshed/replaced; an approved BOM is immutable and remains historical.
13. **Are fractions of panels allowed?** No. Power components use whole PCS; PCS/SET/PAIR require integer counts. M/KG permit fractional quantities. Quantity/unit compatibility is checked against the catalog, not inferred from UI strings.
14. **How is panel DC capacity calculated?** Sum manufacturer rated watts times actual panel counts, divided by 1000. No area-per-kW formula is used. Missing wattage yields null/unverified capacity and a blocking finding, not invented manufacturer data.
15. **What does DC/AC ratio represent?** Installed nominal panel DC capacity divided by inverter rated AC capacity. It is checked against explicitly configured min/max policy, in aggregate and per receiving inverter unit. It is not a generation prediction or a regulatory permission.
16. **Why are policy tolerances explicit?** Capacity deviation, sizing range, voltage headroom and required materials depend on the design/manufacturer context. Each template/configuration stores selected values and a rationale, so reviewers can see the basis instead of hidden universal defaults.
17. **How does MPPT compatibility work?** Designer allocates panels to specific device units/MPPTs and provides sourced design voltage/current bounds. The service checks module counts, conservative assumptions, device input count, cold Voc/headroom, operating voltage and per-input current limits. Missing critical specs blocks approval.
18. **Can correct aggregate capacity hide an overloaded inverter?** No. Per-unit allocation and DC/AC checks detect that case. Inverter/controller maximum PV power is also checked per physical unit, not merely multiplied by all units.
19. **Does every off-grid design require batteries?** The design policy declares battery requirement. External-controller topology requires a bank; batteryless off-grid operation requires affirmative manufacturer inverter support. The API does not silently assume batteryless operation works.
20. **How is battery nominal energy calculated?** Use manufacturer nominal kWh per unit when available; otherwise nominal V × Ah /1000, multiplied by count. Series/parallel bank count must equal BOM quantity. This is nominal energy, not usable energy or autonomy under a real load profile.
21. **Which battery checks are automatic?** A homogeneous bank's declared operating/charge voltage envelope, chemistry, maximum charge/discharge currents and supported inverter/controller interface are checked from available specs. Charging-device ratings are summed conservatively; inverter full-load demand uses minimum bank voltage and supplied conservative full-load efficiency. Mixed banks and dynamic behavior need a separately supported design.
22. **What do unknown specifications do?** They create a COMPATIBILITY_UNVERIFIED or related BLOCKER. Catalog entries/drafts may be incomplete, but they cannot be submitted/approved as compatible. Null outputs distinguish unknown/not-applicable calculations from real zero values.
23. **What is a warning versus a condition versus a blocker?** A blocker prevents submission/approval. A warning communicates a nonblocking deviation or automatic-check boundary. A condition retains unresolved survey/design work and requires explicit reviewer acknowledgement without claiming completion.
24. **How are M02 limitations preserved?** The complete approved survey handoff is copied immutably, including conditions and assumptions. Editable configuration work notes are supplemental. Clearing them cannot erase original M02 conditions, and review snapshots preserve the complete basis.
25. **Who may approve?** An active ADMIN who neither created nor edited that configuration revision/BOM. Both service checks and SQL review guards reject self-review. ADMIN-authored configurations therefore require another ADMIN.
26. **What is atomic during review?** Current survey/catalog/compatibility checks, review snapshot/checklist/notes, configuration decision/version, BOM status and audit entry commit together. Failure rolls back the transaction; no approved status is deliberately committed without a persisted decision.
27. **How are concurrent edits protected?** Current configuration version is required, included in a conditional update and incremented. Child writes and audit use one SERIALIZABLE transaction; stale/version/serialization conflicts return 409 and require a fresh user decision.
28. **Why multiple version numbers?** Template/catalog versions identify reusable definitions. Configuration revisionNumber is a new business record; configuration.version is its edit counter. approvedVersion identifies submitted content N, while approval produces row N+1. BOM.version counts composition/price regeneration, not every status transition.
29. **Can an approved configuration be edited or archived in place?** No. It is terminal/immutable along with its BOM. A new linked revision preserves the previous record and independently validates current survey/template/catalog references. Unapproved/rejected proposals can be archived.
30. **Does approval certify the electrical design?** No. It is internal preliminary component/configuration approval under stated assumptions and limitations. Structural load, protection/cable design, battery operating envelopes, utility/DISCOM/net-metering authorization and commissioning remain separate professional work.
31. **How is API security enforced?** Existing database-backed HttpOnly sessions, role/record scope, trusted Origin, CSRF, strict schemas, bounded bodies/lists and parameterized Prisma queries are reused. Frontend role labels or totals never grant permissions or determine costs.
32. **What can M04 consume later?** The guarded approved configuration reference/version/review and frozen BOM/line definitions, subject to current M02 eligibility and revision status. It must separately determine stock availability and serial/location movements; M03 performs none of those operations.
33. **What was actually verified?** Prisma schema/client generation, strict TypeScript and production build plus source/migration review. No database migration, server, runtime/integration/E2E test, sample product/template/customer configuration or warehouse stock movement was executed.
34. **Why does M03 depend on PR #2?** M02 was still unmerged when work began. M03 branches from its latest reviewed head and adds the latest main frontend unchanged. M02 models/guards/migration must merge/deploy before the dependent M03 migration, not be duplicated or bypassed.
