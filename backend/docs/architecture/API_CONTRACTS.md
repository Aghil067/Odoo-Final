# Backend API contracts index

- [M01 frontend API contract](../integration/M01_FRONTEND_API_CONTRACT.md): `/api/auth`, customer/site/lead CRUD and CRM summary. Existing payload/enum/error conventions remain in force.
- [M02 frontend API contract](../integration/M02_FRONTEND_API_CONTRACT.md): `/api/surveys`, lifecycle, findings, availability, private evidence and versioned approval handoff.
- [M03 frontend API contract](../integration/M03_FRONTEND_API_CONTRACT.md): `/api/solar`, component/template catalog, versioned configurations, exact material BOM and independent review. Depends on M02 PR #2; future-tense M03 statements below record the original boundary.

Both modules use the existing database-backed HttpOnly cookie, exact trusted Origin, per-session CSRF header on unsafe methods, strict Zod validation, `{data:...}` success, top-level list pagination and `{error:{code,message,details?,requestId}}` failures. M02 adds PUT and a narrowly scoped binary upload exception; it does not broaden general CRM permissions. Binary attachment retrieval is the explicit non-JSON response.

M02 adds M01 conflict guards: SURVEY_SITE_LOCKED when changing a surveyed lead's site, ACTIVE_SURVEY_EXISTS when leaving SURVEY_REQUESTED with active surveys. M02 requires that state before request creation and derives identity/capacity from M01, rather than trusting posted customer data.

The future M03 consumer must fetch `/api/surveys/:id/approved`, retain `{surveyId,approvedVersion,reviewId}` and respect recommendation conditions/assumptions. It cannot infer approval from status text supplied by React or an old audit snapshot. No M03 endpoint, design/BOM calculation, token refresh endpoint or frontend adapter is introduced.

The existing frontend's eight lowercase roles/provisional auth interfaces still require explicit alignment with the six uppercase backend roles and real cookie/CSRF response envelopes. See `docs/M02_BACKEND_HANDOFF.md`; do not grant backend privileges by renaming roles in the UI.

M03 reuses `requireApprovedSurvey(tx,user,id)` inside its own write transaction; existing M02 GET `/approved` payload/authorization is unchanged. M03 state/cost/compatibility fields are server controlled, Decimal strings are required, and `/api/solar/configurations/:id/approved` exposes only a current eligible approved revision/BOM reference. No M04 stock operation or frontend rewrite is introduced.

M04: [inventory frontend contract](../integration/M04_FRONTEND_API_CONTRACT.md), `/api/inventory`. Reuses M03 SolarComponent/exact approval guard, Decimal quantities, append-only stock ledger, idempotent stock commands and existing cookie/Origin/CSRF conventions. ADMIN controls setup/adjustments; ADMIN/WAREHOUSE operate stock; FINANCE has oversight reads; SALES/TECHNICIAN have scoped project reads. No generic issue, valuation, installation completion or warranty activation endpoint exists. Earlier future-tense module-boundary descriptions are historical.

M05: [installation API contract](../integration/M05_FRONTEND_API_CONTRACT.md), `/api/installations`, with exact dispatched equipment/site receipt, versioned execution, private evidence and independent commissioning. M04 dependency merged before branching. Existing cookie/Origin/CSRF/error envelopes are reused; binary upload exception now also covers private installation attachments. ADMIN maps to coordinator/reviewer; assigned TECHNICIAN edits only that job; SALES scoped progress, FINANCE commissioned summaries, WAREHOUSE limited equipment references; SUPPORT denied. No later-module API is introduced.

M06: [technician workforce contract](../integration/M06_FRONTEND_API_CONTRACT.md), `/api/technicians`, with private ADMIN/own profiles/qualifications, teams, effective calendars, leave, live availability/workload/conflicts and deterministic human recommendations. Existing User authentication and M02/M05 assignment ownership remain. SALES needs authorized survey context and receives redacted availability. Existing M02 availability adds workforceStatus and stricter available; source staffing may return new409 conflicts without new request fields. No workforce account creation, booking master or auto-assignment is introduced.

M07: [warranty contract](../integration/M07_FRONTEND_API_CONTRACT.md), `/api/warranties`, all51 policy/access/registration/evidence/claim/context/monitoring routes. Reuses cookies/Origin/CSRF, strict validation, Decimal strings and existing envelopes; JSON commands use actor-bound idempotency and versions. ADMIN manages terms/grants and independent final reviews; SUPPORT needs explicit project grants and responsible-reviewer assignment; SALES/TECHNICIAN get scoped limited context; FINANCE approved outcome references; WAREHOUSE no M07 access. Raw private evidence exception is limited to registration/claim evidence POST. M05 commissioned HTTP authorization/payload is unchanged; a scoped internal read helper is reused. No public files, reminder delivery, service ticket or finance operation exists.

M08: [service/maintenance contract](../integration/M08_FRONTEND_API_CONTRACT.md), `/api/service`, all63 ticket/access/triage/escalation/response/assignment/visit/diagnosis/repair/parts/checklist/evidence/feedback/review/SLA/maintenance/context/summary routes. Existing cookie/Origin/CSRF, strict bodies, Decimal strings, versions and actor-bound idempotency apply. ADMIN coordinates/configures/independently closes; SUPPORT needs explicit M08 project grant; current assigned TECHNICIAN updates own field work; SALES scoped summaries; granted WAREHOUSE pending requests; FINANCE closed references. M06 SERVICE purpose/full-window scheduling and M07 actual-actor coverageIn are reused. Only exact ticket evidence POST permits raw private files. No parts usage/stock issue, warranty decision, public portal, finance/analytics backend or delivered notification exists.
