## Models, fields and relations

See `prisma/schema.prisma` for the canonical field definitions. Every model has a UUID primary key generated by Prisma, not an incrementing public identifier.

- **User**: unique lowercased `email`, `name`, `passwordHash`, `role`, `isActive`, creation/update timestamps. Relations to sessions, owned customers, created/assigned leads and actor records. Password hashes never enter API output.
- **Session**: unique SHA-256 `tokenHash`, `userId`, `createdAt`, `expiresAt`. Only the raw random token goes into the HttpOnly cookie. Deleting a user may cascade their sessions; CRM relations restrict user deletion.
- **Customer**: unique `reference`, `type`, `name`, original `phone`, E.164 `normalizedPhone`, nullable `email`, `companyName`, `notes`, `isArchived`, `archivedAt`, `version`, `createdById`, timestamps. One-to-many sites and leads. The phone index is deliberately nonunique.
- **Site**: `customerId`, `name`, `addressLine1/2`, `city`, `state`, `postalCode`, ISO `country`, nullable `landmark`, `propertyNotes`, decimal `latitude/longitude`, `version`, timestamps. The composite unique key `(id, customerId)` is referenced by Lead.
- **Lead**: unique `reference`, `customerId`, `siteId`, `source`, `status`, `priority`, decimal `requestedCapacityKw`, `preferredSystemType`, decimal `monthlyElectricityBill`, nullable `assignedToId`, required `createdById`, nullable `qualificationNotes`, `nextFollowUpAt`, `closedReason`, `version`, timestamps. One-to-many activities and status history.
- **LeadActivity**: `leadId`, `actorId`, actual `type`, `description`, server `createdAt`. Append-only through the API.
- **LeadStatusHistory**: `leadId`, `actorId`, nullable `fromStatus` for the initial enquiry, `toStatus`, nullable `reason`, server `createdAt`. Append-only through the API.

Activity/history rows have no `updatedAt` because the API never edits them. Session expiry likewise does not slide. Monetary values use PostgreSQL `numeric(14,2)` through Prisma Decimal; capacity uses `numeric(10,3)`. Coordinates use `numeric(9,6)` and remain null when unknown.

## Authentication functions and middleware

`hashPassword` generates a 16-byte salt and scrypt-derived 64-byte key with N=32768, r=8, p=1, maxmem=64 MiB. `verifyPassword` performs derivation even when no user is found, compares equal-length buffers with `timingSafeEqual`, and does not expose whether an account exists.

`authRouter` login validates input, checks the active user, verifies the password, rotates any presented session, inserts a new session with bounded expiry, and sends cookie plus `{user, csrfToken, expiresAt}`. Login attempts are limited to 10 per IP per 15 minutes. Invalid input consumes an attempt too. `authenticate` hashes the cookie token, loads its session and user, verifies absolute expiry and active state, and attaches only public user fields to the request.

`actor` refuses requests without a principal. `allowRoles` checks the authenticated role. `requireTrustedOrigin` rejects every unsafe request missing the exact frontend Origin, including login (login-CSRF protection). `requireCsrf` compares the supplied CSRF token with an HMAC derived from the raw session token, using a fixed context string; it is not a second session credential. `/me` returns it for reloads. Logout deletes the current session and clears the cookie. It does not invalidate other devices' sessions.

`publicUser` allowlists `id`, `name`, `email`, `role` for nested lead actor/assignee responses. User password hashes and session hashes are never serialized to clients.

## Controllers, validation and error flow

`crmRouter` first applies `authenticate`, `allowRoles('ADMIN','SALES')` and `requireCsrf`. `id` validates UUID path parameters. Each controller parses the route-specific Zod schema before invoking a service. `list` formats paginated results; `success` is used by single-resource routes. Unknown body/query fields are rejected on CRM routes; clients cannot change `createdById`, `status`, `assignedToId`, customer ownership or timestamps through generic PATCH.

`pageQuery` bounds page to 1–100000 and pageSize to 1–100. `normalizePhone` uses libphonenumber metadata and configured default country; international input is recommended. Invalid numbers/extensions are rejected. Matching numbers/emails produce warnings restricted to visible customer records and are never merged or rejected as inherently duplicate people.

`customerFields` and `siteFields` bound text lengths to their database limits. Nullable optional fields distinguish omitted (retain value on PATCH) from null (clear). Empty strings are rejected. `coordinatePair` requires both latitude/longitude together and limits precision/range. Country is a real ISO alpha-2 code. Postal codes are text, preserving leading zeroes and international formats.

`capacity` and `money` require decimal **strings** and enforce the database precision/scale, nonnegative money and positive capacity. `dateTime` requires an ISO timestamp with timezone and produces a Date; `validateFollowUp` rejects newly scheduled times in the past. Terminal leads cannot be edited or reassigned. Scheduling is done via `PATCH /leads/:id`; logging a FOLLOW_UP activity alone does not schedule one.

Zod errors become HTTP 422 with field paths. Syntax errors become 400; unsupported media 415; payload size 413. Domain errors distinguish 401/403/404/409/422. Database unique/foreign-key/not-found/serialization errors map centrally; unexpected errors return a generic 500 and log only event, request ID and error class. No request bodies, credentials, SQL or stack traces are returned.

## Access functions

- `leadScope`: ADMIN sees all; SALES sees leads assigned to them and unassigned leads they created. A reassigned lead is no longer readable by its former salesperson merely because they created it.
- `customerScope`: SALES sees customers they created or with a lead visible under `leadScope` (assigned to self or own unassigned). Visibility applies to the customer and its physical sites; it does not grant visibility to all other salespeople's leads.
- `requireCustomer`: applies the scope, returns 404 for nonexistent/inaccessible records, and optionally rejects archived customers.
- `requireLead`: applies lead scope, then, for writes, checks active customer access.
- `requireSite`: checks the exact `(siteId, customerId)` pair; a database composite foreign key independently enforces it.
- `checkVersion`: rejects stale edits with 409 before applying a write.

TECHNICIAN, WAREHOUSE, SUPPORT and FINANCE can log in and use `/me`/logout but receive 403 on all CRM routes. Future modules must supply narrowly scoped workflow authorization before these roles gain customer access. No fabricated job-assignment relationship is added here.

## Customer and site services

`duplicateWarnings` queries at most ten visible matches (excluding the current customer on update). `createCustomer` generates `CUS-<uuid>`, persists normalized phone and owner, and returns the row and warning list in one transaction. `listCustomers` combines authorization with name/reference/company/email/phone search, type and archival filters, stable ordering and count-based pagination. `customerDetail` embeds only the first 20 sites and visible leads, with counts and dedicated list endpoints for further pages.

`updateCustomer` checks current version and archive state, recomputes phone normalization when needed, warns on matching visible customers, and increments version. `archiveCustomer` checks all associated leads, including ones not visible to SALES, before setting archival timestamps. Any NEW, CONTACTED, QUALIFIED or SURVEY_REQUESTED lead prevents archival. No hard-delete endpoint exists. Archived customer data remains readable but read-only; unarchive is not implemented.

`createSite` checks an active permitted customer before insertion. `listSites` checks customer visibility before returning a page. `siteDetail` loads the site then checks customer visibility. `updateSite` checks customer access/archive state and version, then updates only address/location fields. Site customer ownership is immutable.

## Lead services and state machine

`createLead` checks active customer, matching site and permitted active salesperson; SALES defaults to self-assignment, ADMIN defaults to unassigned. It atomically creates the lead, initial null→NEW history and real creation activity.

`listLeads` combines scoped search with enum, customer, site, assignee and follow-up filters. `leadDetail` returns persisted customer, site, safe user fields, newest 20 activities and history entries, and pagination counts. `leadTimeline` fetches full paginated activity/history collections after the same authorization check.

`updateLead` requires an open lead and current version, validates optional replacement site, maintains qualification notes on qualified leads and persists changes plus an audit NOTE naming changed fields. Schedule changes additionally append a FOLLOW_UP activity containing the real scheduled timestamp or clearing action. It does not keep a complete before/after snapshot of every field.

`validateSalesperson` checks an active SALES user; ADMIN may choose anyone or unassign, while SALES may only assign themselves within their existing scope. `assignLead` updates the versioned row and saves a NOTE with prior/new assignee IDs. `auditNote` is the shared insertion helper for actual system-generated CRM events.

`transitions` is the dedicated, explicit state machine. `changeStatus` applies it, requires notes before QUALIFIED, requires a reason for LOST/DISQUALIFIED and reopening, permits reopening only to CONTACTED and only by ADMIN, clears follow-up when closing and saves a history row in the same transaction. Same-state requests are rejected. `requireOpen` guards edits/assignment to terminal leads. `createActivity` stores the supplied type/description with authenticated actor and server time; it can record a note on a closed lead but cannot modify an archived customer.

## Transactions and concurrency

`atomic` uses PostgreSQL SERIALIZABLE for all CRM operations. This makes count/detail pages and summary groups internally consistent and protects permission/archive checks against concurrent assignment, lead creation or reopening. PostgreSQL can abort a conflicting transaction; Prisma P2034 maps to 409, without silently retrying a user's action.

Customer, Site and Lead each have a version. PATCH/archive/status/assign requests must carry the current version; successful writes increment it. Prisma updates also include version in the write predicate. A stale version fails; concurrent transactions cannot both apply changes based on the same snapshot. All related writes commit together: lead+creation history+activity, lead patch+notes, assignment+note, status+history. Failure rolls back the complete unit. Activity creation itself is a single append inside an authorization-checking transaction and does not change lead version.

## Summary and request-to-response example

`crmSummary` obtains lead groups, current-state counts, actual follow-up totals/items and distinct qualified-ever lead count from the authorized database snapshot. Conversion is `qualifiedEver / totalLeads * 100`, rounded to two decimal places; a lead that later becomes LOST still counts as historically qualified. No rows means zero counts and empty group/item arrays. `salespeople` provides the admin-only paginated assignment picker, returning no passwords or session details.

Example status request: React sends its cookie, Origin, CSRF header and `{status:'QUALIFIED', version:2}` → global headers/limits/origin/JSON middleware → authentication/role/CSRF → UUID/body schemas → `changeStatus` → serializable transaction → scoped lead and customer reads → version/transition/notes checks → lead update + history insertion → commit → controller returns `{data: lead}`. A thrown error causes rollback and flows to `errorHandler`.

## M02 boundary and limitations

M02 can later consume Lead.id, Customer.id and Site.id when status is SURVEY_REQUESTED, enforcing its own work authorization. M01 does not create a survey, approve a roof, allocate technicians, provision equipment or build an operations map. Coordinates remain optional. M01 approval is required before any other module begins.

No runtime/database behavior was verified in this implementation session. Other explicit limits: no password reset/MFA/user-management UI, unarchive, full field snapshot audit, cross-customer site transfer, arbitrary sorting, distributed rate-limit store, background notification worker or PII erasure workflow. Expired sessions are rejected immediately but need an operator retention job for physical deletion. See the technical document and verification record for deployment gaps.
