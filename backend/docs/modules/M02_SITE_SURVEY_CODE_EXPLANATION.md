## Prisma models and invariants

**SiteSurvey** owns lifecycle, assignment/visit timestamps, expected duration, commercial capacity snapshot, technical recommendation, suitability/conditions, version and approvedVersion. It references the existing Lead using `(leadId,siteId,customerId)` and the existing Site using `(siteId,customerId)`, plus Customer/User FKs. The request's identity/capacity cannot be edited later. `assessmentNumber` and unique `previousSurveyId` form a linear reassessment chain; a new row preserves a terminal predecessor instead of overwriting it.

**RoofAssessment** is one-to-one with SiteSurvey: construction, area, azimuth, tilt, shading, obstructions, mounting area, accessibility/condition, concerns, structural observations, specialist-verification flag and recommendations. Areas/capacity are stored as SQL numeric through Prisma Decimal, not inferred with a universal formula. Angles are recorded observations, with 0° azimuth meaning north and increasing clockwise.

**ElectricalAssessment** is one-to-one: connected/not-connected/unknown supply, phase, meter/panel observations, approximate cable distance, earthing, inverter/battery options, safety flag/concerns and grid notes. These are observations, never certified electrical test readings or utility authorization.

**SurveyAttachment** stores uploader/survey/category, safe display filename, MIME, byte size, SHA-256, private storage key and timestamp. PostgreSQL does not hold raw file bytes. API metadata excludes the storage key.

**SurveyStatusHistory** stores every mutation's actor, server time, event, prior/new states, resulting survey version, reason and structured details. Same-state events distinguish editing, assignment, upload and rescheduling from lifecycle transitions. API and SQL triggers prevent mutation/deletion of history.

**SurveyReview** stores reviewer, decision, reviewed content version, full notes, checklist, and JSON snapshot of the survey, roof, electrical, visit-needed master data and public evidence metadata. A unique survey/version key prevents two decisions for the same submitted version. SQL triggers enforce append-only review rows and review of a currently submitted version by an independent active ADMIN.

## Request → database → response

An ADMIN scheduling request carries the HttpOnly cookie, trusted Origin, X-CSRF-Token and `{version,scheduledAt,expectedDurationMinutes,reason}`. Global security middleware runs first; the survey router authenticates and checks ADMIN, Zod validates timezone/integers, then `scheduleSurvey` opens a serializable transaction. It loads scoped current data, validates version/lifecycle/active surveyor, calculates the end instant and checks existing intervals. `saveSurvey` writes the new slot/version and history, PostgreSQL independently enforces GiST no-overlap, and commit yields `{data: survey}`. Failure rolls back and returns a consistent error. No read-modify-write business operation is split between independent database transactions.

For an upload, origin/session/CSRF/role/query/scope/version checks happen before the raw parser buffers up to the configured size. Signature validation precedes private storage. A second transactional authorization/version check handles reassignment or submission during upload. File write and PostgreSQL commit cannot form one distributed transaction: known failures clean up via the private receipt; uncertain commit failures retain a possible orphan and log a reconciliation event, without risking deletion of referenced evidence. No cleanup job was run or silently introduced.

## Review, revisions and approved versions

Submission changes the row to SUBMITTED; only ADMIN may choose APPROVED, REVISION_REQUIRED or REJECTED. Revision returns the same assessment to an editable state, preserving the earlier review snapshot; a revisit can be scheduled or findings can be corrected without another visit. Full PUT replaces the current structured assessment only while editable. It cannot rewrite the earlier snapshot.

An approval decision references content version N. The decision transition increments the survey row to N+1 and stores `approvedVersion=N`. This distinction is deliberate: M03 must identify the reviewed content, not assume the mutable-row counter equals its approved content version. Approved/rejected/canceled rows are immutable; reassessment requires a new survey ID and next assessment number, linked to the latest terminal predecessor, ADMIN-only, with requestNotes explaining why.

`approvedSurvey` refuses unapproved/rejected/canceled/pending surveys, any survey with a successor, archived customers and leads no longer SURVEY_REQUESTED. It returns immutable approved snapshot, review ID/checklist, recommended capacity/system, conditions and `approvalScope=INTERNAL_PRELIMINARY_FEASIBILITY`. It neither creates M03 records nor claims structural certification, DISCOM approval, net-metering authorization or commissioning.

## SQL migration and concurrency

`backend/prisma/migrations/20261031000200_m02_site_survey/migration.sql` is additive and transactional, generated offline from the M01 schema and augmented with custom constraints/triggers. It enables btree_gist, creates six tables/enums/indexes and the existing Lead composite key, and adds:

- A partial unique index for one active survey per lead and another for one IN_PROGRESS visit per surveyor.
- A GiST exclusion on surveyor UUID and `[scheduledAt,scheduledEndAt)` for SCHEDULED/IN_PROGRESS appointments. Adjacent appointments are permitted; concurrent overlaps fail independently of application checks.
- Range, scheduling, approval, attachment and audit CHECK constraints.
- `m02_guard_survey`, `m02_guard_field_write`, `m02_guard_review` and `m02_append_only` triggers enforcing terminal immutability, stable identity/reassessment chain, one-step version increments, database state graph, draft-only field writes, and append-only decisions/history/evidence metadata.

Service transactions use existing SERIALIZABLE isolation. All survey mutations require the latest version; `saveSurvey` uses conditional updateMany and count=1. Conflicts surface as 409, requiring a fresh read and deliberate retry. PostgreSQL trigger/check SQL has been reviewed statically but not executed. Prisma schema validation does not validate handwritten PL/pgSQL or prove database behavior.

## Limitations and verification

No server, runtime/unit/integration/E2E tests, browser, database migration, fake records or storage uploads were executed. Static validation/build evidence is in M02_VERIFICATION.md. Production still needs approved runtime checks, migration review/extension privileges, private-volume backup/ACLs, malware/content scanning, disk quotas and reconciliation/retention procedures. The adapter validates signatures, not complete image/PDF semantics; downloads are forced and sandboxed. In-memory limits are per process. Appointment availability models confirmed bookings/ongoing visits, not shift calendars, travel or leave. M03 is not implemented.
