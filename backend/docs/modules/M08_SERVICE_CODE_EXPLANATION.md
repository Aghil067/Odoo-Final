# M08 code explanation

`backend/src/modules/service` contains nine focused modules using existing Express5/Zod4/Prisma6.19.3 conventions. No second frontend, User, catalog, stock ledger or workforce calendar is introduced.

- **validation.ts:** exact strict command/query/upload schemas, seven new service enums, explicit nullable source IDs, decimal strings, bounded arrays/text/time windows. Command version means ticket version except plan/grant operations; child writes also carry child version. No schema accepts arbitrary status, customer copies, computed SLA/attendance or replacement serial authority.
- **common.ts:** ADMIN/coordinator/project/ticket role scopes, current technician assignment checks, Serializable wrapper and constraint409 mapping, version-locked ticket lookup, central transition graph, conditional update plus atomic history, canonical body hash and actor-bound idempotency, current-cycle evidence ownership and safe public ticket/evidence projections. Stored warranty context is omitted from ordinary ticket output.
- **integration.ts:** calls actual M05 commissionedRecord; validates selected installed equipment/original M04 serial; delegates to M07 coverageIn with actual actor/scope; returns explicit scope-unavailable uncertainty; verifies optional same-project M07 claim link; validates selected explicit SLA at original opening; coordinates M06 full-window staffing/qualifications and legacy uncertainty acknowledgement.
- **ticket.service.ts:** creation derives customer/site from commissioned source, freezes target, snapshots authorized warranty context and configured SLA. Triage/response/escalation/safety review are explicit. Assignment keeps old rows, locks sorted Users, validates identity/triage skills and waits for personal acknowledgement/timed scheduling. `outstanding` centralizes resolution blockers; mandatory checks use highest ticketVersion and require PASS. Holds preserve heldFrom without pausing SLA. Resolution, staff-attested feedback, independent ADMIN closure and explicit new-cycle reopening/cancellation are separate transactions/commands. Setup grants are project/role-specific and operation-audited.
- **work.service.ts:** visit ownership/current cycle, future scheduling/rescheduling, check-in/out with actual server timestamps, confirmed/denied access, own technician/ADMIN field records, append-only diagnosis revisions and explicit repair lifecycle/outcomes. Starting new repair revalidates staffing within booked window. Follow-up rework preserves before/after audit. Parts only create pending handoffs/explicit cancellations, never fake consumption. Checklist entries append with logical ticketVersion; mandatory NOT_APPLICABLE is rejected.
- **maintenance.service.ts:** explicit immutable sequential SLA revisions, commissioned maintenance plans, pause/reschedule/cancel, one unfinished unique occurrence, idempotent ticket generation through the same `createIn` identity path, real completion and UTC next-due calculation, separate cancellation finalization. Operator-configured intervals/checks replace guessed manufacturer defaults. Plan/SLA operations retain immutable result/reason audit.
- **read.service.ts:** scoped paged collections/filters; redacted sales/warehouse/finance views; current/captured M07 warranty context under current permission; calculated SLA null/elapsed/breach facts; actual due plans/operational counts/workload without assumed labor/utilization or delivered notifications.
- **evidence.service.ts:** authenticated/scope/version preflight, existing signature-safe file validator/private storage, second owner/version/cap check, opaque metadata/digest, atomic ticket version/history, rollback cleanup versus unknown-commit reconciliation, protected integrity downloads. Only coordinator acknowledgement files may append after resolution; closed/cancelled files freeze.
- **routes.ts:** all63 actual endpoints under `/api/service`, role gates, standard envelopes, strict schemas, existing CSRF/cookies, bounded raw binary exception, upload rate limit and protected download headers. No parts-usage, stock-issue, billing or notification endpoint exists.

## Existing integration files

Prisma adds16 models/seven enums plus SERVICE purpose and inverse relations. The additive SQL migration adds constraints/history guards and cross-source scheduling protections, including GiST visit overlap, one running visit, one current ticket assignment, exact ticket/visit ownership and review prerequisites. It extends M06 has_work through a later migration and companion M02/M05/User/profile triggers without editing old migration files.

M06 availability.service extends source queries/capacity/uncertainty and transaction-aware future revalidation to actual service assignments/visits. Its canonical `requiredSkills` helper checks ticket-configured verified qualifications, reused by M08. This avoids a reverse module import/circular scheduling dependency. SERVICE uses full-window eligibility, not coarse installation planning. validation.ts permits the sixth purpose.

M07 read.service extracts `coverageIn(tx,actor,installationId,page,serial?)` from its existing coverage wrapper; public scope/payload remain the same. M08 does not synthesize an ADMIN principal. app.ts mounts service before general CRM and adds only the exact binary evidence POST exception. env.ts/.env.example add optional private service directory/size with no credential. README/architecture indexes link actual contracts. Frontend, dependency files and M01–M07 migrations are unchanged.

## Verification interpretation

Source is statically checked, not runtime-proven. The custom migration remains unapplied; Prisma validation does not execute PL/pgSQL. Actual scheduling races/locks/rollback/timeout/qualification-boundary behavior, private storage and auth/CSRF/API integration need authorized runtime review. No service records, server, seed, migration, runtime tests, M09/M10 backend or automatic merge are performed.

M08 warranty selection retains exact selected equipment/original serial plus project workmanship context; it never treats workmanship as guaranteed equipment-failure coverage. Whole-project tickets use project context. The internal coverage reader accepts this optional filter without changing existing M07 public endpoint behavior. Capture is capped100 matching registrations and exposes coverageTruncated; existing context pagination/claim-history truncation remain explicit.
