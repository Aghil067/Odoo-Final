## Models

- SolarComponent: UUID/SKU, category, name/manufacturer/model/description, structured specifications and source reference, unit, Decimal price/currency, warranty, serialization policy, active flag, version, last change reason, creator and timestamps. It is a product definition, never warehouse stock.
- SolarSystemTemplate: code/name/description, ON_GRID/OFF_GRID, nominal/min/max capacity, explicit validation policy, active flag/version, creator/timestamps.
- SolarTemplateComponent: unique component and position per template, quantity/unit, required flag and notes. Required means at least that component/default quantity remains in the resulting design; optional lines can be removed later.
- SolarTemplateRevision: immutable full template/component snapshot, template version, actor/reason/time. A selected template revision cannot change under an existing configuration.
- SolarConfiguration: UUID/reference, revision series/predecessor, exact lead/site/customer/survey/review/version references, immutable survey/template snapshots, system/phase/target, calculated capacities, assumptions/work requirements, policy/electrical design/report, designer/reviewer, lifecycle/version/time. Composite FKs enforce survey ownership and review/version matching.
- BillOfMaterials: one header per configuration revision, reference/version/status, material total/currency/timestamps.
- BOMLine: one component per header, current selected catalog version, immutable-in-approved-BOM SKU/description/specification/price/category/unit snapshot, Decimal quantity/line total, notes/order/time.
- SolarConfigurationHistory: unique event per configuration optimistic version, actor, prior/new state, reason/details/time; append-only.
- SolarConfigurationReview: immutable decision against a submitted content version with independent reviewer, checklist/notes and complete configuration/BOM/report snapshot.

## Flow and calculations

POST configuration → existing cookie/Origin/CSRF → ADMIN/TECHNICIAN role → Zod → serializable transaction → shared M02 approved/latest/eligible guard → exact version/review comparison → template snapshot/policy selection → configuration/BOM insertion → catalog snapshots → Decimal totals/compatibility findings → initial history → commit → `{data:{configuration,bom,validation}}`. No sample or default catalog/template data is generated.

Line money is quantity × snapshotted unit price, rounded HALF_UP to two decimals; header/category amounts sum those rounded lines. Unit prices retain four decimals, quantities three. Four supported currencies (INR/USD/EUR/GBP) all use two-decimal displayed material totals; no mixed-currency BOM or implicit conversion exists. A 48-digit Decimal context avoids JavaScript floating-point money calculations. Supplied line/header totals are rejected as unknown input fields. Output decimals are strings.

DC kW = sum(panel count × nameplate W)/1000. AC kW = sum(inverter count × rated AC kW). DC/AC ratio, capacity differences and percentage tolerance comparisons use Decimal. Battery nominal kWh is declared per-unit kWh × count, else nominal V × Ah × count /1000 when provided; unknown/not-applicable energy remains null with findings where required. These are nominal material/design calculations, not generation forecasts, bills, tariffs or engineering certificates.

Every panel is allocated exactly once to an explicitly identified receiving device unit/MPPT input; mixed-module sharing of one MPPT is unsupported. Designer-provided cold Voc/hot and maximum Vmp/current assumptions must be documented and at least as conservative as nameplate values. Device ratings, policy headroom, per-input limits, per-unit sizing and controller power are checked; assumptions still need professional verification. One homogeneous battery bank is supported; unsafe/unknown chemistry, voltage/current or charging support blocks approval.

## Lifecycle, snapshots and transactions

DRAFT/REVISION_REQUIRED → READY_FOR_REVIEW → APPROVED/REVISION_REQUIRED/REJECTED. Unapproved records may become ARCHIVED; APPROVED/ARCHIVED have no outgoing changes. Revisions are new rows linked to a terminal predecessor, retaining lead/site/customer identity, with new independently validated survey/template references and fresh current catalog snapshots. Previous approved configurations and BOMs remain immutable.

Configuration version increments on every mutation and protects all child writes. Revision number identifies a new record; BOM version increments only on explicit composition/price regeneration. A reviewed content version N becomes approvedVersion N while the status transition produces row version N+1. Template versions are separate again. Do not interchange these counters.

Initial derived fields are materialized in the creation transaction before initial audit history; SQL permits that narrow version-1 initialization. Later writes use expected-version predicates and serializable transactions. SQL guards protect catalog identity/version, approval state graph, immutable configuration identity and snapshots, append-only template/review/history records, mutable-draft-only BOM lines and independent review. The BOM header status can follow a parent transition without changing its content/version; an already approved header cannot change.

M02 conditions remain in immutable surveySnapshot even if an editable supplemental work note is cleared. Approval acknowledges outstanding work; it does not claim it was completed. Human reviewers cannot approve their own authored/edited revision, including a noncreator who changed BOM pricing/composition. Later survey reassessment or lead/customer ineligibility prevents new M03 edits/approvals/handoffs; history is retained.

## Errors and verification boundary

422 covers invalid fields/units/currencies/required composition/unresolved compatibility/checklist. 409 covers expected-version conflicts, stale catalog/template, immutable/invalid lifecycle, superseded references and SQL serialization/constraints; refresh and decide before retrying. 403 covers forbidden author/reviewer roles/self-approval; scoped missing IDs return 404. Existing generic 401/400/415/413/429/500 behavior remains. No SQL, credentials or stacks are returned.

Prisma validates models and generates types; it does not execute custom SQL guards. Migration is generated but not applied. Typecheck/build are static only: runtime transactions, calculations against real data, SQL trigger execution and browser/API integration remain unverified. See M03_VERIFICATION.md. No M04 backend inventory, seed, stock reservation, serial movement, quotation, installation workflow or frontend redesign is introduced.
